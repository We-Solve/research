\section{Research attempt: Shared style modules can depend on import order}
Let a configuration state contain a font choice $f$. Module $A$ assigns $f=\text{serif}$ and module $B$ assigns $f=\text{sans}$. Importing $A$ then $B$ yields sans, while importing $B$ then $A$ yields serif. Both modules are individually well-defined; the composition is noncommutative. Thus successful reuse of each module does not imply that an unordered collection of modules has a determined meaning.

A finite explicit-map merge can avoid this ambiguity by requiring disjoint exported keys. If modules assign values on pairwise disjoint domains, their union is a function and every key has the same value regardless of merge order. Proof: a key occurs in at most one module, so every ordering takes its value from that same module. More generally overlapping equal assignments are harmless by the same argument, while unequal overlaps must either be rejected or resolved by an explicit priority policy. Priority makes the outcome deterministic but does not prove that it matches the author's intent.

Ambient dependencies cause another failure. Suppose a module reads an unrecorded host variable $h$ and selects serif when $h=0$, sans otherwise. Two projects with identical module bytes and explicit configuration can then render differently. Under a deterministic evaluation model, reproducibility follows only when every observed input is included: if evaluation is a function $R(M,C,H)$, equal triples produce equal outputs by functionality, while equality of just $(M,C)$ is insufficient when $H$ varies observably. Eliminating ambient reads or making them explicit repairs this limited problem. It does not prove portability across different renderer implementations or explain every styling convention.
